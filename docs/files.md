# CryptoCore — устройство проекта по файлам

Документ описывает каждый файл репозитория: за что он отвечает и как работает. Состояние на 19.10.2026, спринты 1–4.

## Общая схема

```
                 cryptocore ...  (setup.py → src.cli_parser:main)
                          │
                 src/cli_parser.py
           ┌──────────────┴───────────────┐
  без подкоманды: шифрование        "dgst": хеширование
           │                                │
  src/csprng.py  (ключ, IV)        src/hash/__init__.py (ALGORITHMS)
  src/modes/*.py (режимы AES)       ├── sha256.py
           │                        ├── sha3_256.py
           │                        └── blake3.py
           └──────────┬─────────────────────┘
                 src/file_io.py  (чтение/запись, ошибки ввода-вывода)
```

Поток данных при шифровании: аргументы → проверка ключа/IV → чтение файла целиком → функция режима → `<IV><шифртекст>` → запись.
Поток данных при хешировании: аргументы → чтение файла кусками по 8 КБ → `update()` хеш-функции → `hexdigest()` → строка `HASH  PATH` → `stdout` или файл.

## `src/` — исходный код

### `src/cli_parser.py` — точка входа и командная строка

Главный модуль. Разбирает аргументы, проверяет их и запускает нужную операцию.

- **`main(argv)`** — точка входа. Если первый аргумент `dgst`, вызывает `run_dgst`, иначе `run_enc`. Шифрование не вынесено в подкоманду, чтобы команды из спринтов 1–3 продолжали работать без изменений.
- **`build_parser()` / `build_dgst_parser()`** — два независимых `argparse`-парсера. У парсера `dgst` вообще нет опций шифрования. В обоих `allow_abbrev=False`: иначе argparse молча принял бы `--enc` вместо `--encrypt`.
- **`run_enc(argv)`** — шифрование и расшифрование:
  1. проверяет сочетания аргументов: `--iv` запрещён при шифровании и в ECB, `--key` обязателен при расшифровании;
  2. `validate_key` / `validate_iv` переводят hex в байты и проверяют длину (16 байт);
  3. `weak_key_reason` ищет очевидно слабые ключи (все байты одинаковые, арифметическая прогрессия, два различных байта) и печатает `[WARNING]`;
  4. без `--key` генерирует ключ через `generate_random_bytes(16)` и один раз печатает его;
  5. для режимов с IV при шифровании генерирует IV и пишет его в начало результата; при расшифровании берёт IV из `--iv` или из первых 16 байт файла;
  6. вызывает функцию режима из словаря `IV_MODES` (или ECB) и записывает результат.
- **`run_dgst(argv)`** — хеширование:
  1. отклоняет любые опции из `ENC_ONLY_OPTIONS` (`--key`, `--iv`, `--mode`, `--encrypt`, `--decrypt`), в том числе в форме `--key=…`;
  2. выбирает класс по имени из `ALGORITHMS`, подаёт в него файл кусками через `iter_input_chunks`;
  3. формирует строку `format_digest_line` и пишет её одними и теми же байтами в `stdout` или в `--output`.
- **`format_digest_line`** — формат `*sum`-утилит `HASH  PATH`. Как в coreutils, если в имени есть `\` или перевод строки, они экранируются, а строка начинается с `\`, чтобы `sha256sum -c` прочитал её правильно.
- **`reject_duplicate_options`** — argparse по умолчанию берёт последнее значение повторённой опции; здесь повтор считается ошибкой.
- **`nonempty_path`** — запрещает пустой путь `--input ""` / `--output ""`.
- Обе команды отказываются писать результат в сам входной файл (`is_same_file`).

### `src/file_io.py` — файловый ввод-вывод

- **`read_input_file(path)`** — читает файл целиком (нужно шифрованию: режимы работают с данными в памяти).
- **`iter_input_chunks(path, chunk_size=8192)`** — генератор, читающий файл в бинарном режиме кусками по 8 КБ; `-` означает стандартный ввод. На этом держится постоянное потребление памяти при хешировании.
- **`write_output_file(path, data)`** — запись в бинарном режиме.
- **`write_stdout(data)`** — пишет байты напрямую в `sys.stdout.buffer`, поэтому вывод не зависит от кодировки терминала и совпадает с содержимым файла `--output`. Если читатель закрыл канал (`| head`), завершается без traceback.
- **`_exit_on_read_error` / `_exit_on_write_error`** — переводят `OSError` в понятные сообщения («файл не найден», «это каталог», «нет прав», «каталог не существует») и завершают программу с кодом 1.
- **`is_same_file`** — через `os.path.samefile` распознаёт один и тот же файл даже по символической или жёсткой ссылке.

### `src/csprng.py` — источник случайности

Функция `generate_random_bytes(num_bytes) -> bytes` — единственный источник случайности в проекте, из неё берутся ключи и все IV.

- Внутри `os.urandom()` — системный CSPRNG (`getentropy` в macOS, `getrandom` в Linux).
- Проверяет аргумент: не `int` (или `bool`) → `TypeError`, отрицательное число → `ValueError`.
- Ошибки ОС (`OSError`, `NotImplementedError`) и неполный результат превращает в собственное исключение `CSPRNGError`; CLI ловит его и завершается с понятным сообщением, не шифруя на плохой случайности.
- Модуль `random` не используется — это проверяется тестом.

## `src/modes/` — режимы блочного шифра

Все режимы реализованы вручную; из pycryptodome берётся только шифрование одного блока AES.

### `src/modes/common.py` — общие примитивы

| Функция | Что делает |
| --- | --- |
| `get_block_cipher(key)` | Объект AES в режиме ECB — используется только как «зашифровать/расшифровать один 16-байтный блок». Неверная длина ключа даёт `ValueError`. |
| `pkcs7_pad(data)` | Дополняет до кратного 16: добавляет `n` байт со значением `n` (1…16). Если длина уже кратна 16, добавляется целый блок из `0x10`, иначе нельзя было бы однозначно снять padding. |
| `pkcs7_unpad(data)` | Проверяет, что последний байт `n` в диапазоне 1…16 и что все последние `n` байт равны `n`, затем отрезает их. Любое нарушение → `ValueError`. |
| `split_into_blocks(data)` | Режет на блоки по 16 байт; последний может быть неполным (нужно потоковым режимам). |
| `xor_bytes(a, b)` | Побайтовый XOR по длине более короткого аргумента — так неполный последний блок XOR-ится с началом гаммы. |
| `check_iv(iv)` | IV должен быть ровно 16 байт. |

### `src/modes/ecb.py` — ECB

`C_i = E_k(P_i)`. Шифрование: padding → блоки → каждый блок шифруется независимо. Расшифрование: проверка кратности 16 → расшифровка блоков → снятие padding. IV нет. Одинаковые блоки открытого текста дают одинаковые блоки шифртекста, поэтому режим небезопасен для реальных данных и оставлен как базовый из спринта 1.

### `src/modes/cbc.py` — CBC

`C_i = E_k(P_i ⊕ C_{i-1})`, `C_0 = IV`. Каждый блок перед шифрованием XOR-ится с предыдущим блоком шифртекста, поэтому одинаковые блоки дают разный шифртекст. Нужен padding PKCS#7. При расшифровании `P_i = D_k(C_i) ⊕ C_{i-1}`; длина шифртекста должна быть ненулевой и кратной 16.

### `src/modes/cfb.py` — CFB-128

`C_i = P_i ⊕ E_k(C_{i-1})`, `C_0 = IV`. Блочный шифр превращается в потоковый: шифруется предыдущий блок шифртекста, результат служит гаммой. Padding не нужен, длина шифртекста равна длине открытого текста. При расшифровании тоже используется `E_k` (не `D_k`). Сегмент 128 бит — как `aes-128-cfb` в OpenSSL.

### `src/modes/ofb.py` — OFB

`O_i = E_k(O_{i-1})`, `O_0 = IV`, `C_i = P_i ⊕ O_i`. Гамма получается многократным шифрованием IV и не зависит от данных, поэтому шифрование и расшифрование — одна и та же функция `_ofb_process`. Padding не нужен.

### `src/modes/ctr.py` — CTR

`C_i = P_i ⊕ E_k(IV + i)`. IV трактуется как 128-битное big-endian число-счётчик, увеличивается на 1 для каждого блока по модулю 2^128 (как в OpenSSL). Шифрование и расшифрование совпадают (`_ctr_process`). Блоки независимы, поэтому режим можно распараллелить.

## `src/hash/` — хеш-функции (спринт 4)

Все три алгоритма написаны с нуля, без `hashlib`.

### `src/hash/common.py` — общий интерфейс

Базовый класс `HashFunction` задаёт интерфейс, который использует CLI:

- `update(data)` — добавить очередную порцию данных (можно вызывать много раз);
- `digest()` — итоговый хеш в байтах; **не портит состояние**, после него можно продолжить `update()`;
- `hexdigest()` — хеш в виде hex в нижнем регистре;
- `hash(data)` — `update` + `hexdigest` за один вызов (удобно в тестах).

У каждого класса есть атрибут `name` — имя для `--algorithm`.

### `src/hash/__init__.py` — реестр алгоритмов

Словарь `ALGORITHMS = {"sha256": SHA256, "sha3-256": SHA3_256, "blake3": BLAKE3}`. CLI берёт из него и список допустимых значений `--algorithm`, и класс реализации. Чтобы добавить алгоритм, достаточно дописать его сюда.

### `src/hash/sha256.py` — SHA-256 (FIPS 180-4)

Конструкция Меркла–Дамгора: состояние из 8 слов по 32 бита последовательно обновляется блоками сообщения по 512 бит.

- **Константы.** `H0` — первые 32 бита дробных частей квадратных корней первых 8 простых чисел (начальное состояние); `K` — первые 32 бита дробных частей кубических корней первых 64 простых (раундовые константы).
- **`update(message)`** — склеивает новые данные с хвостом `_buffer`, обрабатывает все полные 64-байтные блоки, остаток сохраняет. Ведёт счётчик длины `_length`; превышение 2^64 − 1 бит → `ValueError`.
- **`padding(message_len)`** — байт `0x80` (бит `1`), затем нули до длины ≡ 56 (mod 64), затем длина сообщения в битах как 64-битное big-endian число. Если хвост ≥ 56 байт, padding занимает два блока.
- **`process_block(block)`** — функция сжатия:
  1. 16 слов блока расширяются до 64 (расписание сообщения) с помощью `σ0`, `σ1`;
  2. 64 раунда над переменными `a…h` с функциями `Ch(e,f,g)`, `Maj(a,b,c)`, `Σ0(a)`, `Σ1(e)` и константой `K[t]`;
  3. результат прибавляется к старому состоянию по модулю 2^32 (схема Дэвиса–Мейера).
  Циклические сдвиги записаны вручную как `(x >> n) | (x << (32-n))` ради скорости; лишние старшие биты отсекаются маской `& MASK` при сложении.
- **`digest()`** — запоминает состояние, обрабатывает `хвост + padding`, упаковывает 8 слов в 32 байта big-endian и возвращает состояние обратно.

### `src/hash/sha3_256.py` — SHA3-256 (FIPS 202)

Губчатая конструкция (sponge) на перестановке Keccak-f[1600].

- **Состояние** — 25 дорожек по 64 бита (матрица 5×5, всего 1600 бит). Из них rate = 1088 бит (136 байт) — часть, куда впитываются данные; capacity = 512 бит — скрытая часть, которая и даёт стойкость.
- **Константы вычисляются, а не задаются таблицей:** `_rho_offsets()` — смещения ρ по формуле `(t+1)(t+2)/2 mod 64` при обходе `(x, y) → (y, 2x+3y)`; `_round_constants()` — константы ι из LFSR с многочленом x^8 + x^6 + x^5 + x^4 + 1.
- **`keccak_f1600(a)`** — 24 раунда по пять шагов:
  - θ — XOR каждой дорожки с чётностью двух соседних столбцов (диффузия);
  - ρ — циклический сдвиг каждой дорожки на свою величину;
  - π — перестановка дорожек `B[y, 2x+3y] = A[x, y]` (ρ и π объединены в один проход по таблице `RHO_PI`);
  - χ — единственная нелинейная операция `A = B ^ (~B[x+1] & B[x+2])` по строкам;
  - ι — XOR дорожки (0,0) с раундовой константой (ломает симметрию).
- **`update(data)`** — впитывание (absorb): каждые 136 байт XOR-ятся в первые 17 дорожек (little-endian), затем перестановка.
- **`digest()`** — padding `pad10*1` с доменным суффиксом SHA-3 `01`: к хвосту добавляется `0x06`, нули, и в последнем байте блока ставится бит `0x80`. После последнего впитывания из первых 4 дорожек выжимается (squeeze) 32 байта. Состояние восстанавливается.

### `src/hash/blake3.py` — BLAKE3

Третий алгоритм, сверх требований ТЗ. Сочетает функцию сжатия на основе ChaCha с деревом Меркла.

- **`compress(cv, block_words, counter, block_len, flags)`** — функция сжатия: матрица 4×4 из 32-битных слов (значение цепочки, 4 слова IV, счётчик, длина блока, флаги), 7 раундов. Каждый раунд — функция `G` (сложения, XOR, сдвиги на 16, 12, 8, 7) сначала по 4 столбцам, затем по 4 диагоналям; между раундами слова сообщения переставляются по `MSG_PERMUTATION` (порядок заранее вычислен в `SCHEDULE`).
- **Флаги доменного разделения** — `CHUNK_START`, `CHUNK_END`, `PARENT`, `ROOT` — гарантируют, что сжатие листа, внутреннего узла и корня никогда не перепутаются.
- **`_ChunkState`** — обработка одного чанка (1024 байта = 16 блоков по 64): блоки сжимаются по цепочке, первый помечается `CHUNK_START`, последний — `CHUNK_END`. Полный блок сжимается только когда пришли следующие данные, потому что последний блок нужно пометить особым флагом.
- **`_Output`** — «отложенный» последний вызов `compress` узла: из него можно получить либо значение цепочки (для родителя), либо выход корня с флагом `ROOT`.
- **`BLAKE3.update`** — режет вход на чанки; значение цепочки каждого завершённого чанка передаётся в `_add_chunk_cv`.
- **`_add_chunk_cv`** — строит дерево Меркла на стеке: число нулевых младших битов в номере чанка равно числу завершённых поддеревьев, которые нужно слить с соседом. Память — O(log n) значений цепочки.
- **`digest()`** — сворачивает стек снизу вверх в корень и вычисляет 32 байта выхода с флагом `ROOT`.
